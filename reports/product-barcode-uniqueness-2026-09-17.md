# PRODUCT: ป้องกันสินค้าบาร์โค้ดซ้ำ

## ผลการปรับปรุง

- ตรวจรวมบาร์โค้ดหลัก หน่วยเพิ่มเติม บาร์โค้ดสำรอง และบาร์โค้ดผู้จำหน่าย รวมสินค้าปิดใช้งาน
- ปฏิเสธบาร์โค้ดที่เป็นของสินค้าอื่นทั้งตอนเพิ่ม แก้ไข แก้บาร์โค้ดในตาราง และนำเข้า Excel
- ตรวจข้อมูลล่าสุดจากเซิร์ฟเวอร์เมื่อเพิ่ม/เปลี่ยนบาร์โค้ด หากตรวจไม่ได้จะไม่บันทึกและเก็บแบบฟอร์มไว้ให้ลองใหม่
- แก้ราคาโดยไม่เปลี่ยนบาร์โค้ดยังไม่ต้องเรียกตรวจเซิร์ฟเวอร์เพิ่ม
- ไม่ลบเลขศูนย์นำหน้า ไม่ถือช่องว่างเป็นบาร์โค้ด และยังอนุญาตให้สินค้าไม่มีบาร์โค้ด
- ฐานข้อมูลบังคับหนึ่งบาร์โค้ดต่อหนึ่งสินค้า แม้หลายเครื่องส่งพร้อมกัน หรือใช้แอปรุ่นเก่า
- งานซิงก์ที่ถูกปฏิเสธเพราะบาร์โค้ดซ้ำจะพักการส่งซ้ำที่ไม่มีการแก้ไข โดยไม่ทิ้งข้อมูลรอซิงก์
- ตารางเจ้าของบาร์โค้ดสร้างจากข้อมูลสินค้า ไม่ใช่ข้อมูลหลักชุดใหม่ และสร้างกลับอัตโนมัติเมื่อ Restore

## การแก้ข้อมูลเดิมตามที่เจ้าของร้านยืนยัน

บาร์โค้ด **8858981000036** เก็บไว้ที่ **Vesicare 5 mg (30 tablets), P0012**
นำออกจากช่องบาร์โค้ดหลักของ **Vesicare 5 mg (10 tablets), 50513** เท่านั้น
ไม่ได้ลบสินค้า แก้สต๊อก หรือแก้ประวัติบิล สามารถกรอกบาร์โค้ดที่ถูกต้องให้ตัว 10 tablets ภายหลังได้

หลังดำเนินการตรวจฐานข้อมูลจริง: ไม่พบบาร์โค้ดซ้ำ และตารางเจ้าของบาร์โค้ดตรงกับข้อมูลสินค้าทุกรายการ
Migration: `20260917073708_unique_product_barcodes` (ตรงกับฐานข้อมูลจริง)

## การทดสอบ

- Build และชุดทดสอบ Node: ผ่าน 197 tests
- PostgreSQL 17 แยกจาก Production: ผ่าน baseline และ migrations ทั้งหมด รวม backup/restore, checkout, loyalty, quotation และสิทธิ์เข้าถึง
- บาร์โค้ด: ทดสอบทุกประเภท ข้อมูลเก่า สินค้าปิดใช้งาน ช่องว่าง เลขศูนย์นำหน้า การเปลี่ยนและลบสินค้า
- 10 การเพิ่มพร้อมกัน: สำเร็จ 1 รายการ ปฏิเสธบาร์โค้ดซ้ำ 9 รายการ
- Restore ที่มีบาร์โค้ดซ้ำ: ปฏิเสธและ rollback โดยข้อมูลเดิมไม่เสียหาย
- Chrome ข้อมูลจำลอง: เพิ่ม/แก้สินค้า มือถือ ข้อมูลในเครื่องเก่า เซิร์ฟเวอร์ไม่ตอบ ยกเลิกระหว่างตรวจ และ import Excel ผ่าน
- ทดสอบหน้าสินค้าและมือถือซ้ำด้วยไฟล์ production ที่ build แล้ว: ผ่าน
- ชุดทดสอบเบราว์เซอร์เดิม: ทุกไฟล์ผ่าน โดย transfer-document-ui มี timing timeout รอบแรกและผ่านเมื่อรันซ้ำ
- Security Advisor: ไม่มีข้อแจ้งเตือนใหม่จากการเปลี่ยนแปลงนี้ ข้อแจ้งเตือนเดิมยังคงเดิม

ข้อแจ้งเตือนเดิมที่ไม่อยู่ในขอบเขตงานนี้ ได้แก่สิทธิ์เรียกฟังก์ชันที่ออกแบบไว้ และ [Leaked Password Protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) ที่ยังปิดอยู่

## แนวทางที่ใช้

- Skill Supabase และ Supabase Postgres Best Practices: บังคับ uniqueness ด้วยดัชนีจริง ใช้ trigger แบบ private, fixed search_path, จำกัดสิทธิ์ และทดสอบธุรกรรมพร้อมกัน ไม่อาศัยการเช็กหน้าจออย่างเดียว
- Skill Agent Browser / Agent Browser Verify: ตรวจแบบฟอร์มและการตอบสนองจริงในเบราว์เซอร์ เครื่องนี้ไม่มี agent-browser จึงใช้ Playwright/Chrome ที่โครงการมีอยู่ โดยตัดการเชื่อมต่อข้อมูลจริง
- Skill Vercel Deployments & CI/CD และ Vercel API: ลง migration ก่อนเผยแพร่หน้าจอ ตรวจ revision/สถานะ deploy และผล CI ภายหลัง
