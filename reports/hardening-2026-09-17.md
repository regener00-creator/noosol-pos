# ผลแก้ไขจากการตรวจระบบ — 17 กันยายน 2569

## สิ่งที่แก้ไข

1. ไฟล์สำรองเวอร์ชัน 3 ดึงข้อมูลจากฐานข้อมูล ณ snapshot เดียว ครอบคลุม 42 ตาราง รวมกะขาย NOTE ประวัติผู้แทน สินค้าที่ดูแล สิทธิ์ตามคลัง/หน้า ยอดติดลบ/ยอดนอก LOT และประวัติธุรกรรม
2. กู้คืนตรวจจำนวน เนื้อหา/checksum โครงสร้าง และบัญชีผู้ใช้ที่อ้างอิงก่อนเริ่ม ตรวจข้อมูลครบอีกครั้งก่อน commit หากผิดระหว่างทาง rollback ทั้งรายการ ไม่ลบ AUDIT LOG / ประวัติพิมพ์ / ledger ที่มีอยู่
3. การส่งสร้างสินค้าซ้ำหลังคำตอบขาดหายไม่เขียนราคาหรือข้อมูลทับข้อมูลใหม่จากเครื่องอื่น ถ้าข้อมูลต่างกันหยุดให้ตรวจเทียบ พร้อมเก็บงานเดิมไว้
4. ข้อขัดแย้งเดิมพักการส่งซ้ำข้ามการรีเฟรชแบบแยกผู้ใช้ จำกัดขนาดแคชพักงาน และไม่ทิ้งงานใน IndexedDB เอกสารรายการอื่นซิงก์ต่อได้ ไม่บันทึก Error ซ้ำจากสองชั้นสำหรับคำขอเดียว
5. PRODUCT รับการเพิ่ม แก้ไข และลบจากเครื่องอื่น โดยรักษางานในเครื่องที่ยังไม่ซิงก์และตำแหน่งช่องค้นหา/เลื่อนตาราง
6. ปิดการเรียกคำสั่งแก้สินค้ามือถือรุ่นเก่าที่ไม่มี revision โดยตรง ยังคงให้คำสั่งรุ่นใหม่เรียกใช้ภายในได้
7. การตรวจ PRODUCT ที่ไม่มีการเปลี่ยนแปลงลดความถี่จาก 15 เป็นสูงสุด 60 วินาที แล้วกลับมา 15 วินาทีเมื่อพบการเปลี่ยนแปลง รายละเอียดสินค้าโหลดเฉพาะที่เปลี่ยนอยู่แล้ว
8. จัดระเบียบดัชนี 3 ตัวโดยไม่ลบดัชนีหรือประวัติ และปรับ autovacuum/analyze ของตารางที่แก้ไขบ่อย ขนาดฐานข้อมูลที่วัดก่อน/หลังลดจาก 35,220,627 เป็น 26,324,115 ไบต์ (ประมาณ 8.9 MB / 25%) จำนวนสินค้า 2,890 ยอดขาย 10 AUDIT LOG 3,795 และ LOT 8 ไม่เปลี่ยนในช่วงตรวจ

## การทดสอบ

- Node regression 192 รายการผ่าน และ production build ผ่าน
- Browser regression 29 ไฟล์ผ่าน รวมหน้าแยกโหลด 26 เส้นทาง ซ่อม mock บริการ/ลำดับเริ่มต้นของชุดทดสอบที่เคย timeout
- เพิ่ม PostgreSQL 17 แบบแยกในเครื่องทดสอบ ใช้ baseline และ migration จริงทั้งหมด รันได้ด้วย `pnpm run test:database` และรวมอยู่ใน `pnpm test` / GitHub CI เดิม
- ทดสอบ snapshot ขณะอีก connection กำลังแก้หลายตาราง กู้คืนแล้วเทียบเนื้อหาทุกตารางธุรกิจ ไม่ใช่แค่จำนวนแถว
- มีข้อมูลจำลองกะ ยอดขาย รายการขาย เอกสารทุกชนิด NOTE หลายสินค้า ผู้แทน ประวัติหน่วย ประวัติ LOT การตรวจนับ สินค้าโปรด และยอดติดลบ
- ทดสอบไฟล์ไม่ครบ checksum ผิด รุ่นเก่า และ foreign key ผิดระหว่างกู้คืน ต้องปฏิเสธ/rollback โดยข้อมูลเดิมไม่หาย
- จำลอง 10 connections เขียนสินค้า revision เดียวกันพร้อมกัน มีเพียงหนึ่งคำขอสำเร็จ อีกเก้าคำขอไม่ทับข้อมูล
- ทดสอบพนักงานส่งออก/กู้คืนไม่ได้ และคำสั่งมือถือเก่าถูกปิด รวมถึง SQL เดิมด้านแต้ม ประวัติลูกค้า และใบเสนอราคา
- Restore drill สำหรับฐานข้อมูล Supabase ทดลองตรวจ checksum ทุกตารางธุรกิจ และห้ามชี้ Production เดิม
- ตรวจ Production แบบอ่านอย่างเดียวว่า export รุ่นใหม่ทำงานและมีครบ 42 ตาราง ไม่เคยทดลอง restore บน Production

## สิ่งที่ต้องทราบหลังอัปเดต

- รีเฟรชแอปทุกเครื่องเพื่อให้ใช้การป้องกันรุ่นใหม่ ไม่ล้างข้อมูลเว็บไซต์หรือคิวงาน
- ดาวน์โหลดไฟล์สำรองใหม่เวอร์ชัน 3 ไฟล์เก่าต้องเก็บไว้ แต่ระบบจะไม่กู้คืนอัตโนมัติเพราะเดิมขาดข้อมูลสำคัญ
- ไฟล์นี้ไม่รวมบัญชีเข้าสู่ระบบ รหัสผ่าน และคำตอบกู้คืน บัญชีที่อ้างอิงต้องมีอยู่ก่อนกู้คืน ส่วนการตั้งค่าระดับแพลตฟอร์ม/การเก็บประวัติไม่ถูกแทนที่
- งานรอซิงก์บนเครื่องที่ดาวน์โหลดแนบแยกไว้เพื่อตรวจสอบ ไม่ถูกใช้แทนข้อมูลเซิร์ฟเวอร์ขณะกู้คืน จึงต้องซิงก์ทุกเครื่องให้เรียบร้อยก่อนสำรอง/กู้คืน
- ข้อขัดแย้งจริงที่เปิดค้างต้องตรวจจากเครื่องต้นทางและเลือกข้อมูลที่ถูกต้อง ไม่ได้ปิดเหตุการณ์หรือทิ้งงานค้างให้โดยอัตโนมัติ
- ไม่ลบหน้าธุรกิจหรือ ledger ป้องกันธุรกรรมซ้ำเพื่อประหยัดพื้นที่ ไม่ลบดัชนีเพียงเพราะสถิติใช้งานเป็นศูนย์
- ไม่ได้เพิ่มการบังคับเปิด leaked-password protection ซึ่งขึ้นกับการตั้งค่า Auth/แพ็กเกจ และไม่ได้แยกโค้ดส่วนกลางครั้งใหญ่โดยไม่มีผลวัดรองรับ
- ผลทดสอบไม่ใช่การรับรองว่าไม่มีบัคทุกกรณี: ไม่ใช่เครื่องจริง 10 เครื่อง ไม่ได้ทดสอบเครื่องพิมพ์จริง และไม่ได้จำลองบริการ Auth/cron ของ Supabase ทั้งแพลตฟอร์ม
